1. PROJECT HIGH-LEVEL OVERVIEW
================================================================================
Student Management System is a production-grade, enterprise RESTful backend
built using Spring Boot 4 / Java 21, MySQL, Redis, Spring Security, and Docker.
It is engineered to solve core enterprise backend problems:
- Stateless authentication with JWT access tokens and rotatable refresh tokens.
- Secure Role-Based Access Control (RBAC) protecting endpoints based on roles (ADMIN, USER).
- High-performance caching layer powered by Redis to reduce database read overhead.
- Safe data modifications with Optimistic Locking (@Version) preventing lost updates.
- Data integrity retention with Soft Deletes (@SQLDelete, @SQLRestriction).
- Automated audit tracking with Spring Data JPA Auditing.
- Scalable complex querying with JPA Specifications, Projections, and EntityGraphs.
- Full containerization using Docker & Docker Compose with health checks and volume management.

4. CORE MODULES & IMPLEMENTATION DETAILS
================================================================================

--------------------------------------------------------------------------------
4.1. JPA Entities & Advanced Data Modeling
--------------------------------------------------------------------------------
- Student: The core root entity. Contains personal information, authentication
  credentials, role, status flags, audit fields, and relationships.
- Department: Represents academic departments. Linked to students via ManyToOne.
- Course: Represents academic courses. Linked to students via ManyToMany.
- Address: Value-like entity linked to Student via OneToOne.
- RefreshToken: Persisted refresh tokens for session management.
- OtpVerification: Ephemeral records storing time-bounded 6-digit OTP codes.

--------------------------------------------------------------------------------
4.2. Database Design & Relationships
--------------------------------------------------------------------------------
- One-to-One (Student <-> Address):
  Uni-directional/Bi-directional mapping with CascadeType.ALL and orphanRemoval=true.
- Many-to-One (Student -> Department):
  Lazy-loaded ManyToOne relationship ensuring departments are not eagerly loaded.
- Many-to-Many (Student <-> Course):
  Configured using a join table 'student_courses' with foreign keys pointing to
  student_id and course_id.

--------------------------------------------------------------------------------
4.3. Soft Delete & Optimistic Locking
--------------------------------------------------------------------------------
- Soft Delete:
  Implemented using Hibernate annotations:
  @SQLDelete(sql = "UPDATE students SET deleted = true WHERE id=?")
  @SQLRestriction("deleted = false")
  Benefit: Prevents accidental permanent data loss. When delete is called, it flips
  the 'deleted' flag, and all read queries automatically filter out deleted records.
- Optimistic Locking:
  Configured using @Version on 'private Long version;'.
  Benefit: Solves concurrent update anomalies. If two admins edit the same student
  simultaneously, the second transaction encounters an OptimisticLockException,
  handled cleanly by GlobalExceptionHandler (HTTP 409 Conflict).

--------------------------------------------------------------------------------
4.4. JPA Auditing
--------------------------------------------------------------------------------
- Enabled via @EnableJpaAuditing and @EntityListeners(AuditingEntityListener.class).
- Tracks @CreatedDate, @LastModifiedDate, @CreatedBy, and @LastModifiedBy.
- An AuditorAwareImpl component integrates with SecurityContextHolder to capture
  the currently authenticated user's email automatically on create/update.

--------------------------------------------------------------------------------
4.5. Custom Queries & The N+1 Problem Solution
--------------------------------------------------------------------------------
- Problem: Fetching students and their associated address, department, and courses
  can cause 1 + N SQL queries, drastically degrading performance.
- Solution: Used @EntityGraph(attributePaths = {"address", "department", "courses"})
  on custom repository method 'findAllWithDetails()'.
  Benefit: Generates a single SQL query with LEFT OUTER JOINs, cutting database
  round-trips from dozens to just 1.

--------------------------------------------------------------------------------
4.6. Dynamic Filtering with JPA Specifications
--------------------------------------------------------------------------------
- Implemented using Spring Data's JpaSpecificationExecutor and Criteria API.
- 'StudentSpecification.java' dynamically constructs Predicates based on optional
  filter parameters: firstName, lastName, email, and courses.
- Benefit: Avoids writing dozens of brittle repository query combinations.

--------------------------------------------------------------------------------
4.7. Pagination, Sorting & Dynamic Projections
--------------------------------------------------------------------------------
- Pagination: Supports Pageable requests with page numbers, page size, and dynamic Sort.
- Projections:
  - Interface-based: 'StudentProjection' for lightweight read operations.
  - DTO-based: Constructor expressions in JPQL (SELECT new com.dto.StudentProjectionDto(...))
    fetching only the exact required columns, drastically cutting network payload.

--------------------------------------------------------------------------------
4.8. Spring Security, JWT & Refresh Token Rotation
--------------------------------------------------------------------------------
- Stateless Authentication: Configured SessionCreationPolicy.STATELESS.
- Custom UserDetailsService: Loads user credentials directly from Student table.
- JwtAuthenticationFilter: Intercepts requests, validates Authorization header
  ("Bearer <token>"), extracts subject, and populates SecurityContextHolder.
- Refresh Token Rotation:
  When an access token expires (1 hour), the client presents the refresh token.
  The backend verifies expiry, revokes the old refresh token, and issues both
  a fresh access token AND a brand new refresh token (preventing replay attacks).
- RBAC: Configured via requestMatchers:
  - Public endpoints: /auth/**, /swagger-ui/**, /v3/api-docs/**
  - USER & ADMIN: GET /api/students/**
  - ADMIN only: POST, PUT, PATCH, DELETE /api/students/**

--------------------------------------------------------------------------------
4.9. OTP Generation & Gmail SMTP Service
--------------------------------------------------------------------------------
- Secure OTP Generator: Uses java.security.SecureRandom to generate cryptographically
  strong 6-digit OTPs.
- Time-to-Live: OTPs expire in 5 minutes (LocalDateTime.now().plusMinutes(5)).
- Delivery: Integrates Spring Boot Starter Mail with Gmail SMTP (TLS 587) using
  Google App Passwords to deliver verification codes safely.

--------------------------------------------------------------------------------
4.10. Redis Distributed Caching Architecture
--------------------------------------------------------------------------------
- Configured via RedisCacheConfiguration with TTL (10 minutes).
- Serializers:
  - Keys: StringRedisSerializer
  - Values: GenericJacksonJsonRedisSerializer (RedisSerializer.json())
- Cache Patterns:
  - Cache-Aside on Reads: @Cacheable(value = "students", key = "#id")
  - Cache Eviction on Writes: @CacheEvict clears outdated entries on update/delete.

--------------------------------------------------------------------------------
4.11. File Upload & Download Subsystem
--------------------------------------------------------------------------------
- 'FileStorageService' handles student profile pictures.
- Files are saved with unique UUID-based filenames to prevent collisions.
- Validates file paths, creates directories automatically, and serves files as
  Spring Resources with appropriate MIME headers.

--------------------------------------------------------------------------------
4.12. Global Exception Handling & Uniform Responses
--------------------------------------------------------------------------------
- @RestControllerAdvice with @ExceptionHandler classes.
- Standardized ApiResponse<T> containing: success, timestamp, status code,
  message, and data/errors payload.
- Catches:
  - StudentNotFoundException (404)
  - DuplicateEmailException (409)
  - MethodArgumentNotValidException (400 with field-specific validation errors)
  - OptimisticLockException (409)
  - AuthenticationException (401 via RestAuthenticationEntryPoint)
  - AccessDeniedException (403 via RestAccessDeniedHandler)

--------------------------------------------------------------------------------
4.13. OpenAPI / Swagger 3 Documentation
--------------------------------------------------------------------------------
- Configured via OpenApiConfig with @OpenAPIDefinition and @SecurityScheme.
- Integrates Bearer Authentication scheme directly into Swagger UI.
- Developers and clients can interactively test all secured and public endpoints.

--------------------------------------------------------------------------------
4.14. Docker & Docker Compose Containerization
--------------------------------------------------------------------------------
- Multi-Container Orchestration via compose.yaml:
  - Service 1: MySQL 8.4 database with persistent volumes (mysql_data) & healthchecks.
  - Service 2: Redis 7-alpine with ping healthchecks.
  - Service 3: Spring Boot Application container built from Eclipse Temurin JRE.
- Secret & Configuration Externalization:
  - All database credentials, secrets, and hostnames are decoupled into '.env'
    and passed dynamically at runtime without rebuilding images.

7. MASTER INTERVIEW Q&A GUIDE (HOW TO ANSWER QUESTIONS EASILY)
================================================================================

Q1: "How does JWT Authentication and Refresh Token Rotation work in your app?"
A1: "When a user logs in via /auth/login with valid credentials verified by
    AuthenticationManager, the server generates two tokens: a short-lived JWT
    AccessToken (valid for 1 hour) and a persistent RefreshToken stored in MySQL.
    Incoming requests carry the access token in the Authorization header.
    When the access token expires, the client calls /auth/refresh with the refresh
    token. The server verifies its expiry and valid student association, revokes
    the existing refresh token, and issues both a new access token and a new refresh
    token. This rotation ensures that if an old token is intercepted, it is immediately
    invalidated."

Q2: "What is the N+1 problem and how did you solve it?"
A2: "The N+1 problem occurs when fetching a parent entity causes Hibernate to issue 1
    query for the parent and N additional queries for each child relationship. In our
    Student entity, accessing Address, Department, and Courses would cause dozens of
    separate queries. I solved this using @EntityGraph(attributePaths = {...}) on the
    repository method. Hibernate translates this into a single SQL query with LEFT OUTER
    JOINs, reducing database network round-trips from N+1 down to exactly 1."

Q3: "How does Redis Caching work in your application?"
A3: "I implemented the Cache-Aside pattern using Spring Cache annotations.
    When 'getStudentById(id)' is called with @Cacheable(value = 'students', key = '#id'),
    Spring checks Redis first. If the key exists, it returns the cached DTO immediately
    without touching MySQL (Cache Hit). If not found, it queries MySQL, returns the data,
    and stores it in Redis with a 10-minute TTL (Cache Miss). Whenever a student is
    updated or deleted, @CacheEvict automatically purges that student's key from Redis
    to prevent stale data."

Q4: "What is Optimistic Locking and why did you use @Version?"
A4: "Optimistic Locking is a concurrency control mechanism where we assume multiple
    transactions can complete without affecting each other. We annotate a version field
    with @Version in the Student entity. On each update, Hibernate increments this
    version number and includes 'WHERE version = current_version' in the UPDATE SQL.
    If another transaction updated the record first, the version check fails, 0 rows are
    affected, and Hibernate throws an OptimisticLockException. Our GlobalExceptionHandler
    catches this and returns a 409 Conflict, notifying the client to re-fetch fresh data."

Q5: "Why did you implement Soft Delete instead of hard deleting records?"
A5: "In real-world enterprise systems, hard deleting (DELETE FROM) can cause foreign
    key constraint violations and permanently destroys historical audit trails.
    I implemented soft delete using Hibernate's @SQLDelete to execute an UPDATE query
    setting 'deleted = true', and @SQLRestriction('deleted = false') so all select
    queries automatically ignore soft-deleted students without modifying service logic."

Q6: "How did you containerize the project with Docker?"
A6: "I authored a Dockerfile based on Eclipse Temurin JRE to build a minimal image for the
    Spring Boot app. Then I created a compose.yaml orchestrating three independent
    containers: MySQL 8.4, Redis 7, and the Spring Boot application. I configured
    Docker health checks ensuring the application only starts when MySQL and Redis are
    healthy, mapped persistent volumes for database data and uploads, and externalized
    all credentials and hostnames into a .env file."

Q2: "Why did you use JWT instead of normal sessions?"
Simple Answer:
"Traditional sessions are stored on the server memory. If we run multiple server
instances, session sharing becomes difficult. With JWT, all user information is
stored inside the signed token itself on the client side. The server doesn't need to
save any session in memory, making the application stateless and easy to scale."

Simple Answer:
"For security reasons. The Access Token has a short lifespan of 1 hour. If someone
steals it, they can only use it for a short time. The Refresh Token is stored securely
in the database. When the access token expires, the client sends the refresh token to
get a new access token without asking the user to re-enter their password."

Q1: "Can you explain the exact step-by-step flow of JWT in your application?"
Simple Answer:
"1. User sends email and password to /auth/login.
 2. Spring Security verifies the credentials against MySQL.
 3. If correct, the server generates a JWT Access Token (signed with a secret key)
    and a Refresh Token, and sends them back to the client.
 4. For any future request, the client attaches the JWT token in the header:
    'Authorization: Bearer <token>'.
 5. Our JwtAuthenticationFilter intercepts the request, reads the token, verifies
    its signature and expiry, and extracts the username.
 6. If valid, the user is authenticated in the SecurityContext, and the request
    reaches the Controller."

Hinglish Explanation:
"Step simple hai: User login karega -> Backend verify karke token dega -> User agle
har request ke header me token bhejega -> Hamara filter check karega token sahi hai
ya nahi -> Sahi hai toh API access milega, varna 401 Unauthorized."

--------------------------------------------------------------------------------

Q2: "What is inside a JWT token? How does the server know it is not tampered?"
Simple Answer:
"A JWT token has three parts separated by dots:
 1. Header: Contains the algorithm used (like HS256).
 2. Payload: Contains the user data (like email/username, issue time, and expiry).
 3. Signature: Created by hashing the Header + Payload using our secret key.
 If someone modifies the payload (like changing username or role), the signature
 will not match, and the server immediately rejects the token."

Hinglish Explanation:
"JWT me 3 parts hote hain: Header, Payload (user ki details), aur Signature. Signature
hamari secret key se banta hai. Agar koi hacker token me kuch bhi change karega,
toh signature match nahi hoga aur server use reject kar dega."

--------------------------------------------------------------------------------

Q3: "How does Logout work in your JWT implementation?"
Simple Answer:
"Since JWT tokens are stateless and cannot be easily deleted from the client by the
server, we handle logout using our Refresh Token. When the user clicks logout, the
client calls /auth/logout with the refresh token. The backend revokes (deletes or
marks invalid) that refresh token in MySQL. After the current 1-hour access token
expires, the user cannot refresh it and must log in again."

Hinglish Explanation:
"Logout ke waqt client server ko refresh token bhejta hai. Server database me us
refresh token ko delete/revoke kar deta hai. Iske baad jab 1 ghante me access token
khatam hota hai, toh user naya token nahi le pata aur use dobara login karna padta hai."

"I was using my normal Gmail login password in application.properties. Google has

Solution:
"I enabled 2-Step Verification on my Google Account, generated a 16-character
Google App Password, and updated application.properties. After that, OTP emails
were sent instantly without authentication errors."

Challenge 3: "Empty Redis Cache (Cache Miss / Not Showing Data)"
Problem:
"After setting up Redis, I checked Redis CLI using 'KEYS *', but it always showed

"I was testing the 'getAllStudents' API, which did not have the @Cacheable annotation,

getStudentById failed with 404, Spring does not cache exceptions."

'students::1' with the full cached JSON data."

Challenge 4: "Swagger 401 Unauthorized Error even after Authorizing Token"

"After logging in and pasting the JWT token into Swagger's Authorize dialog,

I had typed 'Bearer eyJhbGci...', which caused the header to become
'Bearer Bearer eyJhbGci...', breaking the token parser."
Solution:
"I reopened Swagger's Authorize dialog, logged out, and pasted only the raw token string
without the word 'Bearer'. Swagger sent the clean single 'Bearer <token>' header, and
all APIs worked perfectly."

Hinglish Explanation (Samajhne ke liye):

Q1: What is Inversion of Control (IoC) and Dependency Injection (DI)?

Q2: What is a Spring Bean and what are its common scopes?
- Simple English:
  "A Spring Bean is simply a Java object that is instantiated, configured, and managed
  by the Spring IoC container. Common scopes are:
  1. Singleton (Default): Only one instance is created per Spring container.
  2. Prototype: A new instance is created every time the bean is requested.
  3. Request/Session: Used in web apps; one instance per HTTP request or session."
- Hinglish (Samajhne ke liye):
  "Spring Bean wo Java object hai jise Spring manage karta hai. By default yeh
  Singleton hota hai (poore project me sirf ek hi object banta hai aur sab wahi share

Q3: Difference between @Component, @Service, @Repository, and @Controller?
- Simple English:
  "@Component is the generic stereotype annotation for any Spring-managed class.
  The others are specialized versions with specific roles:
  - @Service: For classes containing business logic.
  - @Repository: For database DAO layers (also translates SQL exceptions into Spring Data exceptions).
  - @Controller / @RestController: For handling incoming HTTP web and REST requests."
- Hinglish (Samajhne ke liye):

  @Service business logic ke liye hota hai, aur @Repository database queries ke liye

Q4: Why is Constructor Injection preferred over Field Injection (@Autowired on field)?
- Simple English:
  "1. Immutability: Dependencies can be declared as 'final'.

  3. Easy Unit Testing: You can easily pass mock objects into the constructor without
     needing a Spring container."
- Hinglish (Samajhne ke liye):

  mushkil hota hai. Constructor injection me variables ko 'final' bana sakte hain aur
  testing me bina Spring ke bhi normal constructor me mock pass ho jata hai."

Q5: What is the Bean Lifecycle in Spring?
- Simple English:
  "1. Bean definition is loaded.
  2. Bean instance is created.
  3. Dependencies are injected.
  4. Initialization callbacks run (@PostConstruct or InitializingBean).
  5. The bean is ready for use.
  6. On shutdown, destruction callbacks run (@PreDestroy or DisposableBean)."
- Hinglish (Samajhne ke liye):

- Simple English:
  "- LAZY: Child data is not loaded from the database until it is explicitly accessed in

   - EAGER: Child data is fetched immediately along with the parent record using a join.

- Hinglish (Samajhne ke liye):

Q13: What is the N+1 Problem and how do you solve it in JPA?
- Simple English:
  "The N+1 problem happens when fetching 1 parent record issues N additional queries for
  each linked child relationship. We solve it using:
  1. JOIN FETCH in JPQL: 'SELECT s FROM Student s JOIN FETCH s.courses'
  2. @EntityGraph: Over the repository method to load relations in one single SQL query."
- Hinglish (Samajhne ke liye):
  "1 student ke sath uske 10 courses laane me agar 1+10=11 queries chalein toh use N+1
  problem kehte hain. Isko @EntityGraph ya JOIN FETCH lagakar sirf 1 single query me
  solve kiya jata hai."

Q14: Difference between save(), saveAndFlush(), and what does @Transactional do?
- Simple English:
  "- save(): Persists entity to Hibernate cache; SQL INSERT may be delayed until commit.
   - saveAndFlush(): Immediately pushes changes to the database in the current transaction.
   - @Transactional: Ensures all database operations within the method run in one transaction.
     If any runtime exception occurs, all changes are automatically rolled back."
- Hinglish (Samajhne ke liye):
  "save() memory me save karta hai aur transaction khatam hone par DB me bhejta hai.
  saveAndFlush() turant DB me SQL bhej deta hai. @Transactional ka matlab agar method me
  beech me koi error aa jaye, toh database me kuch bhi galat save nahi hoga, sab wapas
  rollback ho jayega."

Q15: What are JPA Projections and why do we use them?
- Simple English:

Q16: How does Spring Security work under the hood?

- Hinglish (Samajhne ke liye):

Q17: Difference between Authentication and Authorization?
- Simple English:
  "- Authentication: Verifying WHO you are (e.g., checking email & password or JWT token).
   - Authorization: Verifying WHAT you are allowed to do (e.g., checking if you have the
     ADMIN role to delete a student)."
- Hinglish (Samajhne ke liye):
  "Authentication ka matlab pehchan karna ki 'Aap kaun ho?' (Login).
  Authorization ka matlab haq check karna ki 'Aapko ye kaam karne ki permission hai ya

Q18: Why is JWT called Stateless Authentication?
- Simple English:
  "Because the server does not store any session or user data in its memory. Every incoming
  request carries the complete authentication data inside the self-contained JWT token.
  The server only needs to verify the digital signature using its secret key."
- Hinglish (Samajhne ke liye):
  "Kyunki server apni memory me koi session save nahi karta. Token ke andar hi user ka
  data hota hai. Server sirf secret key se signature check karta hai ki token asli hai ya
  nakli."

Q19: What is CSRF and why do we disable it in stateless REST APIs?
- Simple English:
  "CSRF (Cross-Site Request Forgery) attacks trick a user's browser into sending unwanted
  requests using stored session cookies. In stateless REST APIs where we use JWT tokens
  stored in authorization headers (not session cookies), browsers do not automatically
  send the credentials. Therefore, CSRF protection is unnecessary and disabled."
- Hinglish (Samajhne ke liye):
  "CSRF cookie ke zariye hone wala attack hai. REST API me hum cookies use hi nahi karte,
  balki header me Bearer token bhejte hain jo browser khud se nahi bhej sakta. Isliye
  stateless APIs me CSRF disable kiya jata hai."

Q20: Difference between hasRole() and hasAuthority() in Spring Security?

   - hasAuthority('ADMIN'): Looks for the exact literal match 'ADMIN' without adding any prefix."
- Hinglish (Samajhne ke liye):
  "hasRole('ADMIN') bolne par Spring Security aage khud 'ROLE_' jod kar 'ROLE_ADMIN'
  dhoondhta hai. hasAuthority('ADMIN') bina kisi prefix ke exact wahi word dhoondhta hai."

   - 401 Unauthorized: User is not authenticated (missing or invalid token).

   - 500 Internal Server Error: Unhandled backend server exception."
- Hinglish (Samajhne ke liye):

- Hinglish (Samajhne ke liye):
  "Direct entity bhejne se password ya internal DB columns expose ho sakte hain. DTO
  ek filter ki tarah hota hai jo sirf wahi data bahar bhejta hai jo user ko dikhana hai."

Q25: What is Idempotency in REST APIs?
- Simple English:
  "An HTTP method is idempotent if calling it multiple times produces the exact same
  result on the server state as calling it once.
  - Idempotent: GET, PUT, DELETE.
  - Non-Idempotent: POST (calling POST multiple times creates multiple duplicate records)."
- Hinglish (Samajhne ke liye):
  "Idempotent ka matlab hai API ko 1 baar chalao ya 10 baar, server par asar ek jaisa
  hi hoga (GET, PUT, DELETE). Lekin POST idempotent nahi hai kyunki 10 baar call karne par
  10 naye records ban jayenge."

Q26: What is Spring AI and why was it introduced?
- Simple English:
  "Spring AI is an official Spring project that makes it easy to integrate Artificial
  Intelligence and Large Language Models (LLMs like OpenAI, Gemini, Anthropic, Ollama)
  into Spring Boot applications using clean, standardized Java abstractions without
  writing low-level HTTP calls."
- Hinglish (Samajhne ke liye):
  "Spring AI ek naya framework hai jo Spring Boot ke andar AI models (jaise OpenAI,
  Gemini) ko jodna bohot aasan bana deta hai, jaise Spring Data database ke sath karta hai."

Q27: What is ChatClient and ChatModel in Spring AI?
- Simple English:
  "- ChatModel: The low-level interface that communicates with the specific AI provider
    (e.g., OpenAiChatModel, GeminiChatModel).
   - ChatClient: The fluent, high-level builder API used by developers to send prompts,
    set system instructions, and parse AI responses into POJOs or Strings."
- Hinglish (Samajhne ke liye):
  "ChatModel niche ka engine hai jo AI provider se baat karta hai. ChatClient hamara
  main tool hai jisse hum simple tarike se code likhte hain: chatClient.prompt('Hi').call().content()."

Q28: What is Prompt Engineering and PromptTemplate in Spring AI?
- Simple English:
  "Prompt Engineering is the art of crafting instructions for an AI model. In Spring AI,
  PromptTemplate works like a dynamic message template where you can insert runtime variables
  (e.g., 'Summarize student records for course: {courseName}') safely before sending it to the LLM."
- Hinglish (Samajhne ke liye):
  "Prompt ka matlab AI ko diya gaya sawal ya instruction. PromptTemplate me hum variables
  daal sakte hain jaise '{studentName}', aur run time par dynamic value jud kar AI ke paas jati hai."

Q29: What is RAG (Retrieval-Augmented Generation) in Spring AI?
- Simple English:
  "Standard AI models only know public data up to their training date. RAG is a pattern
  where we retrieve relevant private data from our own database (or documents), append it
  into the prompt as context, and then ask the AI to generate an accurate answer based on our data."
- Hinglish (Samajhne ke liye):
  "AI ko hamari private company ya student data ka nahi pata hota. RAG ka matlab pehle
  apne database se relevant data nikaalna, use AI ke prompt me jodna, aur AI se kehna:
  'Is data ke aadhar par user ke sawal ka jawab do'."

Q30: What are Vector Databases and Embeddings in Spring AI?
- Simple English:
  "- Embeddings: Numerical vector representations (arrays of numbers) of text that capture
    semantic meaning.
   - Vector Database: A specialized database (like PGvector, Chroma, Pinecone) supported by
    Spring AI's VectorStore interface to store these embeddings and perform fast similarity
    searches for RAG applications."
- Hinglish (Samajhne ke liye):
  "Embeddings ka matlab kisi text ko numbers (math vectors) me badalna taaki computer
  uski meaning samajh sake. Vector database un numbers ko save karta hai taaki jab user
  sawal puche, toh milta-julta topic search karke AI ko diya ja sake."
